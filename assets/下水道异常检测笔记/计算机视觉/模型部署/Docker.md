# Docker 模型部署

Docker 是一种容器化部署工具，可以把代码、依赖、运行环境和启动命令封装到统一镜像中。对于深度学习模型部署而言，Docker 的价值在于减少环境差异，使训练、测试和线上推理环境更加一致。

## 一、基本概念

Docker 的核心对象包括镜像、容器、Dockerfile 和仓库。

镜像是静态运行环境，包含系统依赖、Python 环境、项目代码和模型服务所需文件。容器是镜像运行后的实例。Dockerfile 是构建镜像的配置文件，用于描述基础镜像、依赖安装、文件复制和启动命令。仓库用于存储和分发镜像。

可以把镜像理解为“打包好的环境模板”，容器理解为“正在运行的服务实例”。

## 二、部署流程

模型部署的 Docker 流程通常包括以下步骤：

1. 准备模型文件，例如 `.pt`、`.onnx`、`.engine`。
2. 编写推理服务，例如 FastAPI、Flask、gRPC 或命令行脚本。
3. 编写 `requirements.txt` 或环境配置文件。
4. 编写 Dockerfile，指定基础镜像和启动命令。
5. 构建镜像并运行容器。
6. 通过端口映射、日志和接口测试验证服务。

CPU 推理可以使用普通 Python 基础镜像。GPU 推理通常需要使用带 CUDA、cuDNN 或 TensorRT 的基础镜像，并在运行容器时启用 NVIDIA Container Toolkit。

## 三、Dockerfile 结构

一个典型 Dockerfile 包括基础镜像、工作目录、依赖安装、代码复制和启动命令。

```dockerfile
FROM python:3.10-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000
CMD ["python", "app.py"]
```

如果项目依赖 OpenCV，可能还需要安装系统库，例如 `libgl1`、`libglib2.0-0` 等。否则容器中导入 `cv2` 时可能报错。

## 四、模型服务设计

模型服务一般由输入解析、预处理、模型推理、后处理和结果返回组成。

图像输入可以来自文件上传、Base64、URL 或视频流。预处理需要保证与训练阶段一致，例如 resize、颜色空间转换、归一化和维度排列。推理阶段加载模型并输出原始结果。后处理阶段完成 NMS、mask 阈值化、类别映射和可视化。最后以 JSON 或文件形式返回结果。

部署服务时需要避免每次请求都重新加载模型。模型应在服务启动时加载到内存或显存中，请求阶段只执行预处理、推理和后处理。

## 五、常见问题

环境不一致是 Docker 最常解决的问题。不同机器上的 Python 版本、CUDA 版本、依赖包版本不同，容易导致模型无法运行。容器可以把这些依赖固定下来。

镜像过大通常由基础镜像选择、缓存文件、无用依赖和模型文件过多导致。可以使用 slim 镜像、清理缓存、拆分构建阶段或只复制必要文件。

GPU 不可用通常与驱动、CUDA 版本、NVIDIA Container Toolkit 或运行参数有关。容器内的 CUDA 运行环境需要与宿主机驱动兼容。

服务响应慢通常与模型大小、输入分辨率、推理框架和并发策略有关。可以结合 ONNX Runtime、TensorRT、半精度推理、批处理和异步队列优化。

## 六、与 ONNX Runtime 的关系

Docker 解决的是运行环境一致性问题，ONNX Runtime 解决的是模型跨框架推理问题。二者可以配合使用：先将 PyTorch 模型导出为 ONNX，再在 Docker 容器中使用 ONNX Runtime 提供推理服务。

这种方式适合需要跨平台部署、简化依赖和提升推理性能的场景。

## 七、知识总结

Docker 部署的核心思想是把模型运行环境标准化。对于计算机视觉项目，Docker 可以封装图像处理库、推理框架、模型文件和服务代码，减少“本地能跑、线上不能跑”的问题。

一个可靠的容器化模型服务需要关注四点：依赖版本固定、模型只加载一次、预处理与训练保持一致、日志和异常处理完整。Docker 本身不提升模型精度，但可以显著提升部署稳定性和复现能力。
